# Audit 2026-11-25, second report: the architecture

Read at b6da352a: every stage at the level of its files' heads and contracts, the theory (wap/extensions/theory), the
build and test scripts, and what landed on 2026-11-25. Weighed against the plan as it stands at 0ea50f21,
notes/coc-plan.md section 11, track T: one typer, core/analyze, grown in place into the elaborator, with the kernel as
the only maker of checked facts (user 2026-11-25). This report challenges where that plan stops short and spends the
rest on the other stages. Paths are relative to wap/, except those under test/, scripts/ and notes/.

## Target architecture

Built from scratch with what is known now and with the user's track T, wap has one notation, one environment and one
typer.

- **Notation** (Node) is the program as written, and stays the code every stage reads.
  - The reader makes it and knows no word; operators, the shape rules, lowering and `format` read it.
  - Its facts are the text's (position, file, comment, annotations, the spelling written) and the typer's, each type
    fact a judgement the kernel made.
- **The environment** is one persistent value per module: every declaration the module makes, in order, each with an
  id.
  - Its trusted part is the kernel's environment: definitions, inductive types and axioms, which only the kernel adds.
  - The rest is the front's: operator rows and aliases, raw and phrase words, rules, records and signatures, layouts
    and primitives. Lean's environment is built the same way, its kernel's declarations plus extensions.
  - A module is read, shaped and typed inside the environments of the modules it uses.
  - A declaration accepted returns a larger environment; a refusal leaves it as it was.
  - Names resolve to declarations, never to their text.
  - A compiled module carries its environment in its wap section, so the library, a used `.wasm`, the compiler's
    warm start and the seed are one format.
- **One typer**, analyze grown into the elaborator, takes one statement at a time, in one pass, with the environment
  and the type each part is wanted at.
  - Its types are the kernel's terms, shown as notation only in messages and `format`.
  - It fires a kind rule once, in place, on a node whose type is known.
  - Every fact it writes is made by the kernel.
- **Erase** is a stage of its own. It removes types, levels and proofs, and gives each value its layout, a row of the
  table that also holds the primitives (9.7 of the plan). Where an `int` is stored (T8) is a choice of row made there.
- **The emitter** has one case per form and reasons about no type. The runtime (lists, texts, maps, equality,
  printing) is wap in the types module over primitives, for every build. A build (wasm GC, or the memory one for
  native programs) is its table of rows plus the two files that hold a list's items and a text's bytes, chosen by an
  option.

The pipeline: read → operators → shape rules → declare → declared rules → lower → bind → type (the kind rules firing
in it), through the kernel, into the environment → erase → emit → encode.

Today's tree against it:
- **In place:** the reader, the operator table, the shape rules, lowering, the kernel (in the extension until T2) and
  wasm.wap.
- **The environment is spread over seven mechanisms:**
  - Language (23 fields);
  - Module and Signature;
  - Declarations;
  - the warm state;
  - types.wasm with its wap section;
  - the packed format;
  - the kernel's Environment, keyed by text and changed in place.
- **analyze** types by notation compared as text and restarts itself.
- **The emitter** decides layouts, holds a runtime of its own, and types again on wasm layouts.

## Rewrites

Ranked by what they buy. R1 and R2 are the only shrinks on the table and are T's foundation: they should land before
T3.

### R1. One environment per module, carried by the compiled module

**Now.**
- **Language** (core/language.wap: 23 fields, a parameter of 192 functions in 19 files) mixes four things:
  - the language itself;
  - tables kept per file: aliases_of, reading, unparsed, standard, use_free_modules;
  - caches of one compile: operated, lowered, modules, defined_words;
  - the build: readers, memory.
- **Global declarations.** Operators, precedence groups, circumfix glyphs, phrase words and rules are global to a
  compile: a file sees those of every file read before it, used or not. What a file means depends on the order files
  are read (DEBT core/rules/stages.wap:134).
- **Pre-reads.** Building the environment one file is read with takes three scans of its text (its `use` lines; its
  raw words, split out of every line, comments included; the full read) and four walks of its tree before operating
  it. Its uses are worked out four times. Phrase words arrive only after the file is operated (core/pipeline.wap:115-116),
  so the promise at core/pipeline.wap:35, "each file read with the rules of the files before it loaded", does not hold.
- **Identity by text.**
  - A rule's template binds its names where it fires (DEBT sugar/conditions.wap:44).
  - Types are compared by the text of their names, and instances are keyed by text: two classes of one name in two
    modules are one type.
  - The kernel's Environment keys its declarations by text and is changed in place
    (extensions/theory/environment.wap:147-161).
- **The library is held four ways**, and nothing checks at load that they agree:
  - compiled, as types.wasm;
  - as source text in its wap section, read back by the reader (extensions/wasm/modules.wap:44-50, 131-138);
  - operated, in the warm state (extensions/warm.wap);
  - lowered, in the warm state too.

  The 219 rules and 21 patterns are compiled again on every compile.

**Target.** `Environment` is a persistent value of declarations by id, indexed by name, by rule head and by operator
spelling. Each declaration knows its module, and the kernel's part is added to by the kernel alone.
- A module's environment is what the types module and its used modules export, then its own declarations in order.
- A file is read, operated and shaped by its own environment, so a module's rules and operators reach exactly the files
  that use it.
- A template's free words are resolved when its rule is declared, in the rule's module: hygiene.
- Declaring returns a new environment or a refusal. A refused statement, or a typing round started again, leaves
  nothing behind, and nothing is copied.
- Compiling a module writes its environment into its wap section: the front's declarations in the packed format, the
  kernel's in the format extensions/theory/export.wap writes. Using a module, the library or a warm start reads that
  section.

**Deletes and adds** (rough):
- Deletes about 350:
  - Language's per-file and per-compile tables, the pre-reads, and the restart after standard_brought: about 150;
  - warm.wap: 88;
  - library.wap and the source rebuilding in modules.wap: about 110.
- Adds about 280: the environment, about 200; writing and reading the section with packed.wap, about 80.
- Net about −70.

What it buys is not lines. Meaning no longer depends on the order files are read; a name means a declaration; a
compile reads no library source; and LCF facts are never left behind by a refusal (What the plan misses, 3 and 4).

**Unblocks.**
- Module scoping (notes/backbone.md "Open, not built yet"), and rules that belong to their module.
- The compiled library of notes/compile_inputs.md, with one correction (What the plan misses, 7).
- One build step fewer: the warm state is the types module's compiled section.

**Migration**, each step building itself:
1. **Split Language** into the frozen language of the types module and an Environment record per module, which takes
   over the per-file tables. Behavior unchanged.
2. **Scope:** a file is operated and shaped by its own environment. An outcome test pins that a module's rule does
   not reach a file that does not use it (wiki/use.md: `use` brings in a module).
3. **Hygiene:** a template's words are resolved in its rule's module. This pays the DEBT at sugar/conditions.wap:44.
4. **The artifact:** the wap section carries the environment; `use "m.wasm"`, the library and the warm start read it.
   warm.wap and the text round trip go. It needs a seed refresh, done in three steps: write both formats, read the new
   one, drop the old one.
5. **With T2:** the kernel's environment becomes the trusted part, keyed by id and persistent.
6. **A question for the interviewer**, not a step: should a raw word, operator or alias declared in a file apply from
   its line on? Today it applies wherever it stands. If yes, the text scrape and the whole-tree passes go, and the front
   reads one statement at a time.

**Risk:** medium.
- It touches pipeline.wap, language.wap, the rule stages, packed.wap, compiler.wap and the seed's format (step 4).
- Step 2 changes any file that relied on a rule leaking into it; the full suite shows which.

### R2. The emitter decides nothing it can be told

**Now.**
- **Decisions in the emitter.** It has 2,081 lines, 1,406 of them code. Beyond writing each form, it:
  - lays out every type (values.wap);
  - holds the GC build's runtime as 27 routines written as raw instructions, for lists, equality, joining and
    slicing texts, and printing.
- **Its own typing.** It infers types on wasm layouts in about 30 places:
  - a function's result from its body (functions.wap:82-92);
  - a local's type from the code emitted into it (patterns.wap:21);
  - a second "does it fit" beside typing's (emitter.wap:257-290).

  The DEBTs at emitter.wap:22 and :258 say so. It also branches on a type's spelling in 16 lines. The guardrail
  emit-infers-type catches none of this.
- **The memory build** is:
  - 33 branches on `memory`;
  - a library swapped by copying files (extensions/native/build.sh:69);
  - a compile from sources, since the embedded library is the GC one.

  Its runtime is plain wap (types/memory_lists.wap, memory_texts.wap), so the runtime exists twice. The C ABI is a
  third description of layouts: places.wap's C-struct alignment, and the C extension's 66 helper rules that choose
  by a C type's word.
- **The plan:**
  - T1 makes the primitives one table, which is right. Section 9.7 says a prelude type runs by a host layout from
    that same table, but no step moves values.wap's layouts or the runtime routines there.
  - T5 puts erasure into the emitter (+200) and deletes 150 lines of its "shape guessing". The emitter ends at
    2,231 lines (5.3).
  - No step names the DEBTs at emitter.wap:22 and :258.

**Target.**
- The runtime is wap over primitives in types/ for both builds, as the memory build's already is.
- Every layout is a row of T1's table, one table per build (9.7: a prelude type runs by its layout).
- Erase is a stage between the typer and the emitter. It reads the checked statements and writes them without types,
  levels or proofs, each value with its row. Each stage then reads one language and writes one (notes/backbone.md
  "Stage languages"), and T8's storage by context is a choice of row, not emitter code.
- The emitter reads only that: one case per form, no type, no spelling of a type.
- A build is its rows and its two swap files, chosen by an option of the compiler.

**Deletes and adds** (rough):
- The runtime: about 250 lines of instructions (emit/lists.wap, equality.wap and host.wap's printing) become about
  150 of wap, as the memory build's twin is 135: −100.
- The 33 memory branches and the 16 spelling branches become reads of a row: about even.
- The typing on layouts is the "shape guessing" T5 deletes (150), counted there; R2 removes it before T5.
- T5's erasure (+200) moves out of the emitter unchanged.
- Net about −100 beyond T's count. The emitter ends near 1,800 lines instead of T's 2,231.

**Unblocks.**
- T5's erasure on a stage of its own.
- One answer to "does it fit" (the DEBT at emitter.wap:258).
- A native build compiled from the embedded library: no `cp` and no `--sources`.
- The C ABI as rows of the memory build.

**Migration:**
1. With T1, each layout becomes a row beside the primitives.
2. The runtime moves into wap, one routine at a time, written over array and struct primitives. This is a pure move,
   and the emitter shrinks.
3. The memory build becomes an option (its rows and its swap files), and build.sh's copy goes.
4. The emitter reads rows and the checked type; its typing on layouts goes, and the DEBTs at emitter.wap:22 and :258
   are paid.
5. At T5, erasure lands as a stage of its own.

**Risk:** medium.
- The runtime in wap must keep the GC build's speed (list growth, equality), and the benchmarks guard it.
- Steps 1 and 3 change what the seed reads beside it, so they take the careful path.

### R3. A gate blocks or goes

**Now.**
- **One number.** The full suite reports 170 ✗ in 356 tests (test/results.txt, run at b6da352a). Behind it:
  - 94 of the 98 wanted files, red by design;
  - all 62 scripts of test/wap, failing on the host that runs the full suite. It has no wasm2c, so "the installed
    wap runs the modules, not this tree's", and their causes are never written down;
  - programs that need the host's own C library (test_world.wap: "no C function _NSGetEnviron");
  - real failures mixed in, among them test_template.wap (wap refuses lib/template.wap's `mustache`),
    test_graphs.wap and test_collections.wap.
- **Guardrails.** The last local run had 8 of their 16 rules red, with 193 entries over the allowance.
- **The size ceiling.** SIZE_NODES changed in 165 commits since 2026-11-20, each time to the measured value. It
  records the size and limits nothing.
- **About 32 counters and gates in all.**
- **Duplicates.**
  - The build recipe is written twice, and the two differ in the warm state (test/wap/compile.sh:48-55,
    scripts/refresh-seed.sh:39-53).
  - The native wap is built in three places.
  - Four helpers compile and run a program.

**Target.**
- One runner classes each result as passed; wanted (counted, never blocking); skipped, with the host feature it lacks;
  or failed.
- A landing is blocked by a failed line alone.
- A floor rises by itself when a run beats it. A ceiling rises only by a commit that names a decision.
- A guardrail is green and blocking, or deleted.
- One build recipe, which refresh-seed.sh calls.

**Deletes and adds:** about −40 lines of duplicated recipes and helpers, +30 in run.sh. What it buys is signal: the
real failures show, and T's per-step gates (the self-build time, the 17,000-line ceiling) can be trusted.

**Migration:**
1. run.sh classes the results.
2. The ratchets move only by their tool.
3. Each red guardrail is fixed or deleted with the owner of its rule.

**Risk:** low.

### Parts that need no rewrite

- **The reader and cascade:** a data reader that knows no word, linear in its input. Its one coupling, the raw words,
  goes with R1.
- **The operator table and stage:** precedence as relations sorted topologically, aliases as rows, one minus rule.
  With R1 it reads the module's table instead of a global one.
- **The shape rules and lowering:** a pattern and a template over notation is the right macro model, and lowering is
  plain desugaring.
- **analyze, grown in place (T):** no rewrite beyond the plan's, once the foundations in "What the plan misses" 2 to 4
  are laid in T3.
- **Facts in Meta:** they stay the code's facts under T. The kernel's judgement numbers make the type facts checked;
  R1's ids fix the names.
- **The kernel:** Lean's rules with its own term type; T2 moves it in as it is.
- **The seed loop:** self-hosted on the native wap. The seed rule is the price every self-hosting compiler pays, as
  Lean's stage0 does, and 29 refreshes since 2026-11-20 kept it moving.
- **The outcome tests:** per wiki page, a page file kept green and a wanted file whose red lines are the work list. R3
  changes only how results are counted.
- **The native driver and the C extension:** programs of their own on the compiler's output. The C ABI joins R2's rows.

## What the plan misses

**No full rewrite.** T grows the typer in place and keeps the compiler building itself at every step; rewriting
analyze whole would not pay. But T3 to T6 build LCF facts on a typer with three habits the kernel cannot live with
(2 to 4 below), and on a margin of 49 lines (1).

1. **Margin.**
   - T ends at 16,951 of 17,000 lines.
   - Every estimate for T3 to T6 is taken from the extension's elaborator, which works on terms throughout (see 2).
   - The only shrinks on offer are R1 (about −70) and R2 (about −100). They are also T's foundation, so they should
     land before T3.
2. **One type representation.**
   - analyze's types are notation, built and read by core/type_notation.wap and compared by the text of their names
     (core/analyze/fits.wap:186-189). The kernel's are terms.
   - T3 deletes fits.wap and letters.wap, but the other analyze files and the emitter read types as notation.
   - T3 should say that the grown typer's types are terms, shown as notation only in messages and `format`, and its
     cost should count converting the readers.
3. **Restarts under LCF.** analyze starts its typing over in three places:
   - after standard_brought (core/pipeline.wap:202);
   - with a fresh TypingState when a variable was retyped, swallowing that round's errors (core/analyze/types.wap:190-191);
   - when a dispatcher's result changed (:197).

   It types functions again in three more (calls.wap:520-525, letters.wap:60, dispatch.wap:141). Under LCF each round
   makes judgements and declarations in the kernel's table, and the plan does not say what becomes of a discarded
   round's.

   One pass is in reach:
   - the plan's rule that an assignment is a new binding (section 4) turns the variable restart into a second look
     at a loop whose body changes a name's type;
   - T6 removes the dispatcher's;
   - R1 removes standard_brought's;
   - typing a recursive function's header first removes the second typing of a function that calls itself.

   What remains returns to the environment it started from (R1).
4. **The kernel's environment.**
   - T2 moves in an Environment that keys declarations by text and is changed in place
     (extensions/theory/environment.wap:147-161).
   - Under T, two modules' classes of one name are one constant, and a refused statement leaves its declarations
     behind.
   - R1, step 5.
5. **Kind rules under LCF.**
   - Section 5.1 fires the kind rules (3 in wap/) inside the elaborator, on a node once its type is known.
   - Today a kind rule's output is bound at the program's top level and typed again, with no position, and fires
     again on its own output to a depth of 100 (core/rules/typed.wap:24, 38-47). Under LCF each round makes
     judgements.
   - The plan should say that a kind rule fires once, in place: its output bound in the scope of the node it
     replaces, at that node's position, and typed as that node.
6. **The emitter.** T5 puts erasure into the emitter, and no step moves the runtime or the layouts into the table or
   pays the DEBTs at emitter.wap:22 and :258: R2.
7. **The compiled library.**
   - notes/compile_inputs.md wants a compile to need only the library's signatures, its type declarations and its
     rule tables.
   - That cannot hold once library definitions unfold in types and laws: a module's artifact carries the bodies that
     may unfold, as Lean's compiled modules do (R1).

The questions on one typer, against T:

| item | removed by | enough? |
|---|---|---|

| bridges: `prim` bodies, `runs(…)`, hosted spellings | T1: a `runs(…)` body is a primitive of the table, no spelling is typed | yes; the text bridge (run/lower.wap) leaves at T7 |
| literal defaults | T3: a numeral has the type its place wants, else `int` | yes |

| doors | T7: one compile, and `wap check` on the explicit spellings | yes |
| overloads | T6: overloads become instances; until then they are ranked by weights (DEBT core/analyze/calls.wap:329) | yes, at T6 |
| effects against Prop | T6: computation types, and a proof refuses an impure function | yes |
| annotations in operated code | not in the plan | the first audit's R1.9, about 5 lines in core/parse; with R1, an annotation that leads a statement belongs to it |

## Appendix: evidence

1. **The environment built by scraping (R1).**
   - core/parse/raw.wap:19-26 finds the raw words by splitting every line of the source on brackets and colons,
     comments included.
   - `import "x"`, a spelling of `use`, is missed by the `use` detection (core/pipeline.wap:86, :95), which looks for
     the text "use " before aliases apply, so x is read after the file that uses it.
2. **Declarations printed and read back (R1).**
   - A used module's declarations travel as wap source and header lines (extensions/wasm/modules.wap:44-50,
     131-138).
   - Rules are told apart by their printed text (core/rules/stages.wap:112).
3. **A build made by `cp` (R2).** extensions/native/build.sh:69 copies memory_texts.wap and memory_lists.wap over
   text_bytes.wap and list_items.wap in a copy of the compiler's folder. It then compiles with `--sources`, because
   the embedded types.wasm is the GC one.
4. **Identity by text (R1; What the plan misses 2 and 4).**
   - `same_type` compares a type's name (core/analyze/fits.wap:186-189), and Node's `==` ignores Meta, where
     DECLARED_BY lives.
   - An instance's key is the text "<id> <name> <signature>" (core/stage.wap:194-196).
5. **A restart that swallows its errors (What the plan misses 3).** core/analyze/types.wap:190-191 types the program
   again with a fresh TypingState when a variable was retyped, and drops that round's refusals.
6. **A gate that records (R3).** test/wap/ratchet_census.sh's SIZE_NODES went from 100,896 to 142,947 in 165 commits,
   each moving it to the measured value.
